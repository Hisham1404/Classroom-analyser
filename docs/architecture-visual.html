01

The constraint that shapes everything

The obvious design transcribes on demand: a visitor uploads audio, the app runs Whisper, results appear. That design cannot be built here, and three separate measurements say so independently.

ConstraintMeasuredConsequence
Local CPU transcription0.42× realtime≈30 h to process the corpus with whisper-hindi-medium
Streamlit Community Cloud1 GB RAMCannot hold a 1.5 GB model in the serving process
HF ZeroGPU, unauthenticated2 min GPU / dayOne 60-minute file exhausts a reviewer's entire daily quota

This is also the honest shape of the real product. A phone in an Igatpuri government school records for an hour and syncs when it finds a signal. Batch-then-serve is production, not a shortcut — and it matches the offline-first platform MakerGhat says it is building.

02

System architecture

The pipeline is split by robustness, not by convenience. Everything in the language layer degrades as the room gets louder. Everything in the signal layer does not. The load-bearing metrics are deliberately built on the half that survives.

StageDoesNotable
01 IngestValidate, decode to 16 kHz monoDeclared duration disagrees with the actual stream on 3 of 5 files — every denominator uses the decoded length
02 SignalSilero VAD, then split non-speech by energyHands-on (loud, children building) vs dead (quiet) — the maker-education distinction
03 LanguageWhisper-hi, IndicTrans2, question detectionPer-segment avg_logprob is kept as an input to M6, not as diagnostics
04 AttributionBinary teacher vs studentThe phone is the teacher's, so she is the loudest, nearest voice — energy alone is a strong feature
05 MetricsM1–M5Four acoustic and robust; one lexical and gated
06 GateScore confidence, decide what is shownCan refuse to report at all
03

The signature view

One picture carries the product. The timeline strip shows the shape of a lesson at a glance — and, crucially, it still works when every word in the transcript is wrong, because it is built entirely from the signal layer.

04

The data contract

One JSON per session is the boundary between offline and online. Everything upstream can be rewritten freely as long as this shape holds — which is what makes the ASR model swappable without touching the app. 

// results/OD11165_2026-01-06-114155.json  — abridged
{
  "session_id": "OD11165_2026-01-06-114155",
  "teacher": { "id": "OD11165", "alias": "Teacher B" },   // name never persisted
  "activity": "Trumpet",
  "roster": { "total": 8, "boys": 5, "girls": 3 },

  "audio": {
    "declared_sec": 4134.6,     // from their JSON — untrusted
    "actual_sec":   3858.0,     // decoded — the only denominator used
    "completeness": 0.933,
    "speech_density": 0.856
  },

  "timeline": [
    { "t0": 12.4, "t1": 19.8, "kind": "speech", "role": "teacher",
      "role_conf": 0.91, "is_question": true, "asr_logprob": -0.61,
      "text_hi": "यह किससे बनाया है?", "text_en": "What is this made from?" },
    { "t0": 23.1, "t1": 61.5, "kind": "handson" }
  ],

  "metrics": {
    "M1_teacher_talk_ratio":      { "value": 0.615, "benchmark": 0.40, "confidence": 0.78 },
    "M4_longest_teacher_stretch": { "value": 412,   "unit": "sec",  "confidence": 0.85 },
    "M5_wait_time_1":             { "value": 0.8,   "unit": "sec",  "confidence": 0.41 }
  },

  "confidence": { "overall": 0.71, "verdict": "usable" },
  "flags": ["clipping_detected"]
}

Two decisions are load-bearing. alias, never name — the raw teacher name stays out of any file that could be committed. And every metric carries its own confidence, not just the session, so wait time can be suppressed while talk ratio is still shown.

05

Knowing when to say nothing

The confidence verdict changes the whole page, not a footnote on it. On our own data the Shadow Art session — 27 students, 20% speech density, the loudest file of the five — should land in the third column. That refusal is the demo worth showing.

usable

Full report

confidence ≥ 0.65

  • All five metrics shown
  • Bilingual transcript
  • One concrete suggestion
  • WhatsApp summary sent
partial

Acoustic only

0.40 – 0.65

  • M1–M4 shown
  • Wait time suppressed
  • Transcript marked approximate
  • Suggestion drawn from talk shape only
unreliable

Refuse to report

< 0.40

  • No metrics at all
  • "Too noisy to analyse"
  • Recording tips instead
  • No WhatsApp numbers sent

A dashboard that admits it cannot read a room is more useful to a teacher than one that invents a statistic — and more defensible to the M&E team that has to stand behind the number. Most submissions will print a confident figure for that file.

06

How the teacher sees it

Santana teaches 22 children in a government school in Igatpuri. She has a phone, patchy data, about five minutes, and no interest in machine learning. MakerGhat already reaches her through MakerDost, a WhatsApp bot — so the browser dashboard is the M&E team's surface. Hers is a message.

  1. RecordOpens the M&E app, taps record, teaches, taps stop. No signal in the classroom, so it stores locally.
  2. SyncThe phone uploads when it finds wifi — hours later, usually at home.
  3. ProcessBatch pass transcribes, attributes, scores. She is not waiting on it.
  4. One messageA WhatsApp message with the headline and a single thing to try. If confidence was too low, she gets recording tips instead — never a fabricated number.
  5. Detail, if she wants itTapping the link opens the timeline, four cards, and the transcript. Most weeks she won't, and that's fine.
  6. Next monthThe trend view shows her own two sessions side by side. We have two each for Santana and Sudipto, so this is real, not hypothetical.

MakerDost · WhatsApp

नमस्ते Santana! आज की क्लास में आपने 62% समय बात की। मेकर सेशन में 40% से कम बेहतर रहता है। आपका सबसे लंबा हिस्सा 6 मिनट 52 सेकंड का था — बीच में एक सवाल पूछकर देखिए।

Hello Santana! You spoke 62% of the time today. Under 40% works better in a maker session. Your longest unbroken stretch was 6m 52s — try breaking it with a question halfway through.

The design goal is that step 4 is enough. If she never opens the dashboard, she still got one usable thing out of the hour she recorded.

How everyone else sees it

The M&E lead

A different question entirely: not "how was my lesson" but "which teachers need support, and is our data any good?"

Wants to knowScreen element
Which sessions are analysable at allCoverage strip — usable / partial / unreliable
Which teachers are improvingTrend lines per teacher
Where capture is brokenData-quality table — truncation, clipping, missing GPS
Whether maker sessions differ from lecturesActivity-type breakdown

The truncation finding belongs on this screen. Three of the five recordings are shorter than their own metadata claims — 42, 20 and 5 minutes missing. That is an operational bug in the capture app, and surfacing it is worth more to MakerGhat than any single lesson metric.

The reviewer, in the first thirty seconds

Worth designing explicitly, because a mandatory live link that greets a reviewer with a spinner has already lost. Each step answers something they said they were grading.

  1. Opens the URLA session is already loaded with full results. No upload, no spinner, no cold model.
  2. Reads the headline and timelineUnderstands what the product does before reading a word of the README.
  3. Switches to the Shadow Art sessionWatches the app decline to analyse it. System design thinking.
  4. Uploads a 90-second clipProves nothing is hardcoded. Tool integration.
  5. Opens eval/asr_bakeoff.mdThree ASR models, hand-scored on the same clips, with an honest note that clean-benchmark WER does not transfer to a room with 25 children in it. AI/ML understanding.
